# Process Designer — Phase 3.6: Multi-input crypto, AAD and random bytes

## Mission

Extend the Process Designer so cryptographic operations can consume multiple visual inputs through named ports. The immediate goal is AES-GCM with AAD, externally supplied IV/nonces, and secure random bytes. This is a laboratory application: execution traces must show all operational values (including keys, IVs, AAD and generated bytes), while `.cfprocess.json` persistence must still remove secret keys and passwords.

Do not implement WSS-Security in this phase.

## Context and non-negotiable compatibility requirements

The current model has `ProcessDefinition`, `ProcessEngine`, `ProcessNodeHandler`, typed `FlowValue`, and `ProcessDefinition.Connection.targetPort`. It already supports the ports `payload`, `key`, and the special VERIFY `payload` / `signature` inputs.

Recent defects must not return:

- Existing links without a target port to operations with `payload + key` mean `payload`.
- A legacy connection named `payload` to a single-port console/file output must normalize to its sole `input` port.
- Duplicate links are forbidden only when they target the same destination port. The same source may legally feed two different ports of one target.
- Never add nested, local or anonymous production classes. The workspace synchronizer has renamed generated `$...class` files as conflicts, causing `NoClassDefFoundError`. New production classes must be top-level source files.
- No behaviour may rely on a stale `target/` directory. Verify from `mvn clean test`.

## Functional scope

### 1. Generic port-aware connection UX

Replace the current hard-coded `VERIFY` and `key` button branching with generic behaviour driven by `ProcessNodeHandler.inputPorts(node)`.

When exactly two blocks are selected, selection order is **source then destination**. The UI must offer all currently valid destination ports by their semantic names and descriptions, for example:

| Destination | Choices |
| --- | --- |
| AES-GCM Encrypt | `payload — data to encrypt`, `key — AES key`, `iv — IV/nonce`, `aad — additional authenticated data` |
| AES-CBC Encrypt | `payload`, `key`, `iv` only |
| AES-GCM Decrypt | `payload — ciphertext`, `key`, `iv` when RAW ciphertext is used, `aad` |
| VERIFY | `payload`, `signature` |

Requirements:

- Prefer one scalable `MenuButton` / contextual menu labelled **Connect to…** over a growing row of special buttons.
- Disable or hide occupied ports and show a helpful message instead of silently replacing a connection.
- Show named labels at the receiving end of each connection (`payload`, `key`, `iv`, `aad`, `signature`).
- Retain normal two-block connection behaviour for a destination with one unambiguous port.
- Connection reversal must not produce invalid port names; either map a valid new port deliberately or reject it with a concise explanation.
- The inspector must explain a selected node’s ports and representation contract.

### 2. AES-GCM AAD as a first-class input

For `ENCRYPT` and `DECRYPT`, dynamically expose the optional `aad` port only when the selected algorithm is `AES/GCM/NoPadding`.

- AAD accepts `TEXT_UTF8`, `BINARY`, `HEX`, `BASE64` and `BASE64URL` flow values; consume their bytes exactly as provided.
- Pass AAD to the existing `SymmetricCipher.encrypt(..., aad)` and `decrypt(..., aad)` APIs.
- With a non-empty AAD, decryption must fail authentication if AAD differs or is absent.
- AES-CBC/PKCS7 and AES-CTR must not expose or accept AAD.
- Keep AES-GCM output `RAW` by default; `ENVELOPE` remains an explicit mode. AAD is not implicitly invented during decrypt: a RAW GCM decrypt needs the same AAD connection/configuration.

### 3. IV / nonce as a connectable input

Support an optional `iv` port for `ENCRYPT` and `DECRYPT`:

- It accepts `BINARY` only. Use an explicit HEX/Base64 decode node before connection if needed.
- A supplied `iv` input takes precedence over the inspector field and auto-generation.
- Required lengths: GCM 12 bytes; CBC and CTR 16 bytes. Validate with an actionable error naming the port, expected length and actual length.
- If no IV input exists, retain the current inspector behaviour: Encrypt can auto-generate and displays/persists the public IV; RAW decrypt requires a configured IV.
- An IV used from an upstream node must appear in the lab trace in full hex and be marked as `source: flow`.

### 4. Random bytes source node

Add `RANDOM_BYTES` under a new palette category **Generators** (or a concise submenu under Crypto if the current layout requires it).

Configuration:

- Length in bytes, default `16`, allowed range `1..65536`.
- Source is `SecureRandom`; never use `Random`, timestamps, or deterministic fallback.
- Output is `FlowValue.binary` and representation `BINARY`.
- Node title shows the configured length, e.g. `Random bytes (16 B)`.
- Inspector explains typical uses: IV/nonce, AAD, test payload. It must not imply random bytes are automatically a valid AES key unless their length is selected appropriately.
- Trace logs the generated bytes in uppercase hexadecimal because this is a laboratory tool.

Expected use cases:

1. `Random bytes (12 B) → Encrypt.iv` for AES-GCM.
2. `Random bytes (16 B) → Encrypt.iv` for AES-CBC/CTR.
3. `Console input → Encrypt.payload`; `Console input/File input → Encrypt.aad` for AES-GCM.
4. `Random bytes → Console output` for inspection.

### 5. Raw/interoperable crypto semantics

Keep the recently established output semantics:

- Default output is `RAW (standard ciphertext)`.
- AES-CBC is labelled `AES/CBC/PKCS7Padding`. The Java provider may implement its equivalent through `PKCS5Padding`, but this implementation detail must not leak into the Process Designer UI or trace.
- `ENVELOPE (self-describing workflow value)` remains selectable for self-contained chaining, with its purpose explained.
- AES-CBC output for identical plaintext, key and IV must exactly match the Symmetric Cipher Workbench.

### 6. Observability and no redaction in this laboratory surface

For this Process Designer lab only, trace all operation inputs/outputs in a readable form:

- Step, node label/type, selected algorithm, named input ports, representation, byte count and value.
- Full hex for `BINARY`; text as text; exact Base64/Hex source strings where appropriate.
- Identify whether a key/IV/AAD came from configuration, auto-generation or a flow port.
- Execution Status table must populate deterministically after execution and include all final states.

Do not change `ProcessDefinitionCodec` secret stripping: `key`, `keystorePassword` and `keyPassword` must still never be written to process files.

## Architecture guidance

- Add a top-level `RandomBytesNodeHandler` class; register it in `ProcessEngine`.
- Evolve `AdvancedCryptoNodeHandler.inputPorts(node)` dynamically based on the selected cipher algorithm. Do not hard-code port choices in the controller.
- The handler execution path should retrieve `payload`, `key`, `iv`, and `aad` from the `Map<String, FlowValue>` by named port, with configuration fallback only where specified above.
- Keep key byte array clearing in `finally`. Do not clear a flow value’s shared byte array in place; clone before clearing.
- Preserve representation validation and cycle detection. Add validation for port names, duplicate binding to the same port, and IV lengths.
- Avoid new inner classes/records/enums in production code. Use top-level classes or primitive/static helper methods.

## Required tests

Add or update focused tests. Tests must be deterministic where expected: use explicit keys/IVs/AAD rather than generated values.

1. `RandomBytesNodeHandler` emits the configured number of bytes and `BINARY` representation; invalid lengths fail fast.
2. AES-GCM encrypt/decrypt succeeds with payload + key + 12-byte IV + AAD from separate nodes.
3. The same GCM decrypt fails with changed AAD.
4. An IV flow overrides a configured IV; tested for GCM and CBC.
5. CBC raw output with `Hola`, fixed key and IV equals the Symmetric Workbench vector.
6. CBC/CTR reject an `aad` port during validation.
7. Two connections from one source to two distinct destination ports are valid; a second connection to the same port is rejected.
8. Legacy unlabelled payload connections and legacy `payload → Console output` remain compatible.
9. JavaFX controller test: select random bytes then AES-GCM Encrypt and assert **Connect as IV/nonce** appears; select a text source and assert **Connect as AAD** appears.
10. JavaFX controller test: the execution table has final rows and the trace exposes the IV/AAD/random values without literal `\\n` sequences.
11. Serialization test: generated values may be logged at runtime, but process serialization still strips manual keys and passwords.

Run and report exactly:

```bash
mvn clean test -Dtest=ProcessEngineTest,ProcessEnginePhase35FileTextTest,ProcessDesignerControllerTest,OperationRegistryTest
git diff --check
```

If the known `GnuPgInteropTest` is run separately and fails due to local non-interactive GPG, report it separately; do not count it as validation of this work.
